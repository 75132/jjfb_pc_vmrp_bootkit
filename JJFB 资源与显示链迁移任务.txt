7. 旧 bridge 的 mr_drawBitmap 实现
旧版 ABI：
mr_drawBitmap(
    uint16_t *bmp,   // R0
    int16_t x,       // R1
    int16_t y,       // R2
    uint16_t w,      // R3
    uint16_t h       // [SP]
)
旧实现行为：
1.从 R0-R3 和 SP 读取参数；
2.验证 bmp、w、h；
3.Guest LCD buffer 按 SCREEN_WIDTH pitch；
4.只复制 dirty rect；
5.写入 host RGB565 framebuffer；
6.标记 dirty；
7.不在每次 draw 后立即无条件 present；
8.由 _DispUpEx 或 timer flush 合并显示。
旧版等价逻辑：
for (j = 0; j < h; ++j) {
    yy = y + j;
    if (yy < 0 || yy >= screen_h) continue;

    for (i = 0; i < w; ++i) {
        xx = x + i;
        if (xx < 0 || xx >= screen_w) continue;

        host_fb[yy * screen_w + xx] =
            guest_lcd[yy * screen_w + xx];
    }
}

mark_dirty(x, y, x + w, y + h);
注意：
mr_drawBitmap 的 R0 可能是完整 Guest LCD buffer，
不是一张 w×h 的紧凑 bitmap。
所以 pitch 必须根据该 API 的真实语义使用屏幕宽度。

8. 旧 bridge 的 _DrawBitmap 实现
旧 bridge 观察到两种 ABI。
8.1 Classic ABI
R0 = pixels
R1 = x
R2 = y
R3 = w

SP+0  = h
SP+4  = rop
SP+8  = transparent color / flags
SP+12 = source x
SP+16 = source y
SP+20 = source pitch / image width
8.2 Robotol wrapper ABI
旧版识别条件：
stack arg0 == R3
语义：
R0 = pixels
R1 = x
R2 = y
R3 = source pitch / image width

SP+0  = w
SP+4  = h
SP+8  = rop
SP+12 = flags
SP+16 = source x
SP+20 = transparent color
旧版选择逻辑：
wrapper_abi =
    ((stack_arg0 & 0xFFFF) == (R3 & 0xFFFF))
    && stack_arg0 != 0;
如果是 wrapper ABI：
pitch = R3
w     = SP+0
h     = SP+4
rop   = SP+8
src_x = SP+16
src_y = 0
trans = SP+20
如果是 classic ABI：
w     = R3
h     = SP+0
rop   = SP+4
trans = SP+8
src_x = SP+12
src_y = SP+16
pitch = SP+20
必须使用：
pitch = source image width
不能用裁剪后的 w 作为 pitch，否则画面会扭曲。

9. 旧 bridge 的透明色规则
旧版主要使用 RGB565。
明确有效的透明色：
0xF81F
旧版判断：
trans == 0xF81F
或 trans >= 0x100
小整数可能只是 rop/flag，不能都当颜色。
旧实现还会在角落像素包含 0xF81F 时把它作为后备透明色。
正式产品建议：
优先使用 Guest 参数传来的 trans
其次使用资源对象中已证明的透明色字段
最后才能使用角落探测作为兼容策略
不得根据资源文件名：
wy_
slogo
bar
jiantou
直接决定透明色。旧版这种文件名启发式只能留作诊断对照。

10. 旧 bridge 的 _DispUpEx 实现
旧 ABI：
R0 = x
R1 = y
R2 = w
R3 = h
如果 w/h 非法或不大于 0：
刷新整个屏幕
旧版行为：
present_flush("DispUpEx");
return MR_SUCCESS;
关键原则：
Draw 只修改 host framebuffer 和 dirty rect；
DispUpEx 才执行正式 SDL present。
旧版还使用 timer-end 作为 backup flush，因为 Guest 不一定频繁调用 _DispUpEx。
当前正式产品：
优先以 Guest _DispUpEx 为 present 边界；
如果证明旧平台语义需要 timer-end flush，可以加入通用的 frame coalescing flush；
不得每次 _DrawBitmap 都强制全屏 present。

旧版 E9E 中：

16. caller object 写入
旧版写入了 Guest caller object，随后 Guest 自然返回 bitmap handle。
当前不能照抄旧固定 object offset。
做法：
1.在当前自然资源请求调用处记录 R0-R3/SP；
2.观察调用者返回后读取哪些字段；
3.以实际 load/store 指令确定 out object ABI；
4.实现对应字段；
5.不构造最终 bitmap handle；
6.让 Guest 继续解析 decoded bytes。
只有证明调用 ABI 与旧 E9E 完全一致时，才复用旧字段布局。

18. RGB565 blit
实现 binary-safe RGB565 copy。
基本逻辑：
for (int yy = clip_y0; yy < clip_y1; ++yy) {
    const uint16_t *src_row =
        src
        + (yy - dst_y + src_y) * src_pitch
        + src_x
        + (clip_x0 - dst_x);

    uint16_t *dst_row =
        framebuffer
        + yy * screen_width
        + clip_x0;

    for (int xx = clip_x0; xx < clip_x1; ++xx) {
        uint16_t p = *src_row++;

        if (key_enabled && p == transparent_key) {
            ++dst_row;

22. Import/slot 绑定原则
所有能力按正式平台身份绑定：
API ID
slot index
mr_table offset
module import identity
禁止按调用 PC 绑定。
旧 bridge 已知 mr_table 图形偏移参考：
mr_drawBitmap = mr_table + 0x74
_DispUpEx     = mr_table + 0x1D8
_DrawPoint    = mr_table + 0x1DC
_DrawBitmap   = mr_table + 0x1E0
_DrawBitmapEx = mr_table + 0x1E4
_DrawText     = mr_table + 0x1EC

这些 offset 只能用于验证当前 table identity，不得在 Guest 任意地址写补丁。
若当前 shadow table 对应 slot 为空或错误：
修复 table 构建/注册逻辑
不得像旧 bridge 一样通过运行期 heal shadow gfx 扫固定 offset 偷写。
